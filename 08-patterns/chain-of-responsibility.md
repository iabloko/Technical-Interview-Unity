# Chain of Responsibility (цепочка обязанностей)

Поведенческий паттерн: запрос проходит через цепочку обработчиков; каждый либо обрабатывает его и останавливает цепочку, либо передаёт дальше. Снимает «лес `if/else`», где каждый случай — отдельная проверка.

## Когда применять

Упорядоченные обработчики, каждый из которых может обработать или пропустить:
- фильтры/обработка ввода;
- модификаторы урона (броня → сопротивления → щит);
- пайплайн валидации;
- миграции сохранений;
- обработка событий по приоритету.

## Форма

```csharp
public interface IHandler<T>
{
    bool Handle(T request);   // true — обработал, цепочка останавливается
}

public sealed class HandlerChain<T>
{
    private readonly IReadOnlyList<IHandler<T>> _handlers;
    public HandlerChain(IEnumerable<IHandler<T>> handlers) => _handlers = handlers.ToArray();

    public bool Handle(T request)
    {
        foreach (var h in _handlers)
            if (h.Handle(request))
                return true;
        return false;
    }
}
```

- Обработчики внедряются как `IEnumerable<IHandler<T>>` через [DI](../02-architecture/di.md). **Порядок важен** — регистрировать явно.
- Новый обработчик добавляется новым классом без правки существующих — [OCP](../02-architecture/solid.md).

## Варианты

- **«Кто-то один обрабатывает»** (как выше): первый подходящий завершает.
- **Пайплайн-конвейер**: каждый обработчик трансформирует запрос и обязательно передаёт дальше (как middleware) — все по очереди.

## Отличие от соседних

- Vs **switch/if-цепочка**: CoR делает набор правил расширяемым и тестируемым по одному.
- Vs [Strategy](design-patterns.md): Strategy выбирает **один** алгоритм; CoR прогоняет запрос через **последовательность** обработчиков.

## Что спрашивают на собеседовании

- Какую задачу решает CoR (убрать жёсткий `if/else`, расширяемые правила).
- Почему важен порядок и как его задают (явная регистрация в DI).
- Как соотносится с OCP.
- Разница с Strategy.
