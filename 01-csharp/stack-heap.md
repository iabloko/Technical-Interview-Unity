# Стек и куча (Stack / Heap)

В .NET память исполняемого кода делится на два основных региона: **стек** (stack) и **управляемую кучу** (managed heap).

|              | Стек (Stack)                                     | Куча (Heap)                  |
|--------------|--------------------------------------------------|------------------------------|
| Что хранит   | локальные переменные, параметры, адреса возврата | объекты (reference-типы)     |
| Порядок      | LIFO (последним вошёл — первым вышел)            | произвольный                 |
| Освобождение | автоматически при выходе из метода               | сборщиком мусора (GC)        |
| Скорость     | очень быстро (сдвиг указателя)                   | медленнее (поиск места + GC) |
| Размер       | маленький, фиксированный (риск `StackOverflow`)  | большой                      |
| Доступ       | по значению                                      | по ссылке                    |

---

## Стек

- Своя область стека у каждого потока.
- Хранит **value-типы**, объявленные как локальные переменные, и параметры методов.
- При вызове метода создаётся **stack frame**; при выходе — снимается целиком (мгновенное освобождение).
- Переполнение (например, бесконечная рекурсия) → `StackOverflowException` — её **нельзя поймать**, процесс падает.

```csharp
void Foo()
{
    int x = 5;          // value-тип — на стеке
    Vector3 v = ...;    // struct — на стеке
}                       // x и v исчезают при выходе из метода
```

## Куча

- Общая для всех потоков (нужна синхронизация при доступе).
- Хранит **reference-типы**: сами объекты лежат в куче, а ссылка на них — на стеке (или в другом объекте).
- Освобождается **GC**, когда на объект не остаётся достижимых ссылок.

```csharp
var player = new Player();  // объект Player — в куче,
                            // ссылка `player` — на стеке
```

---

## Value-типы vs reference-типы: где они живут

Частая ловушка: «struct всегда на стеке» — **неверно**.

- **Локальная** value-переменная — на стеке.
- Value-тип как **поле класса** — лежит **в куче**, внутри объекта-владельца.
- Value-тип, **захваченный замыканием** или в `async`-методе, — переезжает в кучу.

```csharp
class Enemy
{
    Vector3 _position;  // struct, но лежит в КУЧЕ — внутри объекта Enemy
}
```

> Точнее говорить не «где тип», а «где конкретный экземпляр» — это зависит от контекста.

## struct vs class (кратко)

|               | `struct` (value)            | `class` (reference) |
|---------------|-----------------------------|---------------------|
| Где экземпляр | стек / там где владелец     | куча                |
| Семантика     | копирование по значению     | по ссылке           |
| `null`        | нет (если не `Nullable<T>`) | да                  |

## Инструменты для работы со стеком (без аллокаций)

- `Span<T>` / `ReadOnlySpan<T>` — работа с памятью без выделения в куче.
- `stackalloc` — выделение буфера на стеке.
- `ref struct` (например, `Span<T>`) — тип, который **обязан** жить только на стеке.

```csharp
Span<int> buffer = stackalloc int[16];  // буфер на стеке, ноль аллокаций в куче
```

## Почему это важно в Unity

- Любая аллокация в куче нагружает GC; срабатывание GC даёт **спайк кадра** (стоп мир) — критично для 60 FPS и VR.
- Правило: **избегать аллокаций в `Update`/горячих путях** — не создавать в них `new`, не провоцировать boxing, переиспользовать буферы и пулы.
- `struct` (`Vector3`, `Quaternion`) специально сделаны value-типами, чтобы не мусорить в куче.

### Как делать НЕ надо

```csharp
void Update()
{
    // 1. new коллекции каждый кадр → мусор в куче на каждый кадр
    var visible = new List<Enemy>();

    // 2. LINQ создаёт итераторы и замыкания → скрытые аллокации
    var closest = _enemies.Where(e => e.IsAlive).OrderBy(e => e.Dist).First();

    // 3. конкатенация/интерполяция строк → новая строка + boxing чисел
    _label.text = "Score: " + _score;        // boxing int → object
    Debug.Log($"FPS: {_fps}");               // строка строится, даже если лог отключён

    // 4. boxing value-типа в object/интерфейс
    object boxed = transform.position;        // Vector3 уехал в кучу — см. [Boxing / Unboxing](boxing-unboxing.md)

    // 5. лямбда с захватом переменной → новое замыкание каждый кадр
    _button.onClick.AddListener(() => Use(_score));

    // 6. foreach по тому, что аллоцирует IEnumerator (boxing IEnumerator у некоторых типов)
    foreach (var kv in _someDictionaryViaInterface) { }
}
```

> Как надо: создавать коллекции/буферы один раз и переиспользовать, выносить LINQ из горячего пути, собирать строки через `StringBuilder` или обновлять текст только при изменении, кэшировать делегаты, применять пулы объектов.
