# Многопоточность и синхронизация

## Базовые сущности

| Сущность | Назначение |
|---|---|
| `Thread` | отдельный поток ОС. Дорогой (≈1 МБ стека), создавать пулами, не на каждую задачу |
| `ThreadPool` | переиспользуемый пул потоков для коротких задач |
| `Task` / TPL | абстракция над пулом, композиция через `async/await`, `ContinueWith` |
| `Parallel` | data-параллелизм (`Parallel.For`, `Parallel.ForEach`) |

`Task.Run` ставит делегат в `ThreadPool`. Это конкурентность через потоки, в отличие от `async/await`, который сам по себе **не создаёт потоков** (см. [async](../05-async/async.md)).

## Проблема: гонки данных (race condition)

Несинхронизированный доступ нескольких потоков к общим данным, где хотя бы один пишет, даёт недетерминированный результат. Операция вида `count++` **не атомарна** (read-modify-write из трёх инструкций) — два потока могут потерять инкремент.

## Средства синхронизации

| Средство | Что делает |
|---|---|
| `lock (obj)` | критическая секция; сахар над `Monitor.Enter/Exit` в `try/finally`. Только один поток внутри |
| `Monitor` | то же явно + `Wait`/`Pulse` для условий |
| `Interlocked` | атомарные операции без блокировки: `Increment`, `Add`, `Exchange`, `CompareExchange` |
| `Mutex` | межпроцессная блокировка (тяжелее `lock`); см. [глоссарий](glossary.md) |
| `SemaphoreSlim` | ограничение N одновременных доступов; есть `WaitAsync` |
| `ReaderWriterLockSlim` | много читателей **или** один писатель |
| `volatile` | запрет кеширования/переупорядочивания чтений-записей поля (см. ниже) |

```csharp
private int _count;
// Небезопасно: _count++;
Interlocked.Increment(ref _count);   // атомарно, без блокировки

private readonly object _gate = new();
lock (_gate) { /* критическая секция */ }
```

## volatile и модель памяти

Компилятор, JIT и CPU могут переупорядочивать инструкции и кешировать значения в регистрах. `volatile` гарантирует, что чтение всегда берёт актуальное значение из памяти, а запись сразу видна другим потокам, и запрещает переупорядочивание относительно этого поля (acquire/release-семантика). `volatile` **не делает составные операции атомарными** — для `++` всё равно нужен `Interlocked`.

## Взаимоблокировка (deadlock)

Два потока захватывают два ресурса в обратном порядке и ждут друг друга вечно. Профилактика: единый порядок захвата блокировок, минимальные критические секции, таймауты (`Monitor.TryEnter`).

## Специфика Unity

- **Unity API не потокобезопасен.** Обращаться к `Transform`, `GameObject`, большинству методов движка можно только из главного потока. Из фонового потока — только чистые вычисления (математика, парсинг, IO).
- Возврат результата в главный поток: `SynchronizationContext`, очередь задач, или [UniTask](../05-async/async.md) (`SwitchToMainThread`).
- Для высоконагруженного параллелизма в Unity предпочтителен [Job System + Burst](../07-dots/jobs-burst.md): безопасность по данным проверяется, нет аллокаций и боксинга.

## Что спрашивают на собеседовании

- Чем `async/await` отличается от многопоточности (асинхронность ≠ параллелизм).
- Почему `count++` небезопасен и как чинить (`lock` vs `Interlocked`).
- Что делает `volatile` и чего не делает.
- Как избежать deadlock.
- Почему нельзя трогать Unity API из другого потока.
