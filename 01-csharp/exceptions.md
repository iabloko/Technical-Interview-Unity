# Исключения: механизм и стоимость

## Механизм

`try`/`catch`/`finally` + `throw`. При выбросе среда раскручивает стек (stack unwinding), ищет подходящий `catch` вверх по цепочке вызовов, по пути выполняя блоки `finally`. Если обработчик не найден — необработанное исключение завершает поток/процесс.

```csharp
try { Risky(); }
catch (IOException ex) { /* конкретный тип выше по списку */ }
catch (Exception ex)   { /* общий — последним */ }
finally { /* выполнится всегда: освобождение ресурсов */ }
```

- `catch` упорядочивать от частного к общему.
- `finally` выполняется при нормальном выходе, при исключении и при `return` из `try`.
- `using` — синтаксический сахар над `try/finally` с вызовом `Dispose` (см. [управляемая память](managed-unmanaged-memory.md)).

## Стоимость (важно)

- **`throw` дорог.** Захват трассировки стека и раскрутка — на порядки дороже обычного `return`. Исключения — для **исключительных** ситуаций, не для управления потоком выполнения.
- **`try` без выброса почти бесплатен** в .NET: пока исключение не брошено, накладные расходы минимальны. Дорог именно момент `throw`/раскрутки.
- Не использовать исключения для ожидаемых исходов (например, «элемент не найден») — для этого `TryGet`-паттерн (`bool TryParse(out …)`), возврат кода/`null`/Result-типа.

## Хорошие практики

- Ловить **конкретные** типы, а не `catch (Exception)` без разбора.
- Не «глотать» исключения пустым `catch {}` — теряется диагностика.
- Пробрасывать с сохранением стека: `throw;` (не `throw ex;` — последнее затирает исходную трассировку).
- Свои исключения — наследовать `Exception`, добавлять контекст.
- `finally`/`using` для гарантированного освобождения ресурсов.

## Специфика Unity

- **Исключение в `Update`/корутине/колбэке не «роняет» игру**, но логируется и прерывает текущий вызов метода; корутина при исключении завершается целиком и на следующих кадрах не продолжается. Частичное выполнение может оставить объект в неконсистентном состоянии.
- В hot path исключения как поток управления → спайки (захват стека аллоцирует).
- В [Burst](../07-dots/jobs-burst.md)-коде исключения в общем случае не поддерживаются (только ограниченно, для отладки).
- `async`-методы: исключение хранится в `Task`/`UniTask` и всплывает при `await`. Без `await` вызывающий код исключение не получает: из `async void` оно публикуется в `SynchronizationContext` (в Unity — логируется), из `UniTaskVoid` — передаётся в `UniTaskScheduler.UnobservedTaskException` (по умолчанию логируется), из неожидаемого `Task` — остаётся ненаблюдаемым (`TaskScheduler.UnobservedTaskException`) (см. [async](../05-async/async.md)).

## Что спрашивают на собеседовании

- Что происходит при `throw` (раскрутка стека, поиск `catch`, `finally`).
- Почему исключения дороги и почему не для control flow (TryGet вместо).
- Разница `throw;` и `throw ex;` (сохранение трассировки).
- Когда выполняется `finally`; что такое `using`.
