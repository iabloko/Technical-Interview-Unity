# Загрузка ассетов: Resources / AssetBundles / Addressables

Три способа подгружать контент в рантайме. Главный вопрос на собесе — **когда какой** и **почему Addressables вытеснил остальные**.

## Коротко

| | Resources | AssetBundles | Addressables |
|---|---|---|---|
| Ссылка на ассет | строка-путь | имя бандла + имя ассета | `AssetReference` / ключ / лейбл |
| Где лежит | внутри билда (всегда) | отдельные файлы (локально/CDN) | группы → бандлы (локально/CDN) |
| Удалённая доставка | нет | вручную | из коробки |
| Управление памятью | ручное, только массовая выгрузка | ручное (`Unload`) | ref-counting + `Release` |
| Дублирование ассетов | частое | контролируешь сам | анализатор зависимостей |
| Статус | legacy | low-level | **рекомендуемый** |

## Resources

Любой ассет в папке `Resources/` **безусловно** включается в билд (независимо от того, ссылается ли на него сцена) и загружается по строковому пути.

```csharp
var prefab = Resources.Load<GameObject>("Enemies/Goblin");
Resources.UnloadUnusedAssets(); // массовая выгрузка всех ассетов без ссылок
```

**Минусы (почему не использовать):**
- Всё содержимое `Resources/` объединяется в единый serialized-файл с таблицей метаданных всех ассетов; она **строится и загружается при старте**, поэтому увеличивает **время запуска** приложения тем сильнее, чем больше ассетов в `Resources/`.
- Загруженный ассет остаётся в памяти до явной выгрузки, а выгрузка неадресная: `UnloadUnusedAssets()` сканирует все загруженные объекты и выгружает только те, на которые не осталось ссылок (дорогая операция, обычно вызывается на экране загрузки). Выгрузить конкретный ассет можно лишь `Resources.UnloadAsset()`, и то с ограничениями по типам.
- Строковые пути → нет проверки на компиляции, легко сломать при переименовании.
- Нельзя обновить контент без пересборки приложения.

**Когда оправдан:** крошечный набор данных, нужный с первого кадра до инициализации систем загрузки. В остальных случаях — нет.

## AssetBundles

Низкоуровневый механизм: ассеты пакуются в **бандлы** — отдельные файлы, которые можно положить локально или на CDN и грузить по требованию.

```csharp
var bundle = AssetBundle.LoadFromFile(path);
var prefab = bundle.LoadAsset<GameObject>("Goblin");
// ...
bundle.Unload(true); // выгрузить бандл и загруженные из него объекты
```

**Плюсы:** удалённая доставка и обновление контента без пересборки; гранулярная загрузка/выгрузка; разбиение игры на DLC.

**Минусы (всё это и решают Addressables):**
- Ты **вручную** ведёшь: какой ассет в каком бандле, граф зависимостей, версии, кэш, хэши.
- Легко получить **дублирование**: общий ассет, не вынесенный в отдельный бандл, копируется в каждый зависимый.
- Нет встроенного ref-counting — сам следишь, когда `Unload(true)` безопасен.
- Разные пути и кэш под платформы — много ручного кода.

## Addressables

Надстройка **над AssetBundles**: тот же механизм бандлов, но Unity берёт на себя адресацию, зависимости, кэш и подсчёт ссылок. Ассет грузится по **адресу** (ключу), а не по физическому расположению — где он лежит (в билде / локально / на CDN) решается настройками группы, код не меняется.

```csharp
[SerializeField] private AssetReferenceGameObject _enemyRef; // типобезопасно, из инспектора

var handle = _enemyRef.LoadAssetAsync<GameObject>();
var prefab = await handle.ToUniTask(cancellationToken: ct);
// ...
Addressables.Release(handle); // на каждый Load — ровно один Release
```

**Плюсы:**
- **Decoupling** ссылки от расположения: перенёс ассет с диска в CDN — код тот же.
- **Ref-counting**: бандл с зависимостями выгружается автоматически, когда счётчик дошёл до нуля (выгрузка — целым бандлом, см. [Addressables](addressables.md)).
- **Анализатор зависимостей** ловит дублирование; группы решают, что пакуется вместе.
- Async-загрузка, лейблы для запросов пачкой, remote-каталог и обновление контента.
- `AssetReference` вместо строк: ссылка хранит GUID ассета, назначается в Inspector и не ломается при переименовании или перемещении ассета (проверку выполняет редактор, не компилятор).

**Минусы / частые ошибки:**
- **Утечки**: забыл `Release`/`ReleaseInstance` — ref-count не дойдёт до нуля и бандл останется резидентным в памяти. Каждый `Load`/`Instantiate` парен с релизом на всех ветках (успех, отмена, исключение).
- `Object.Destroy` на объекте из `InstantiateAsync` **нельзя** — только `ReleaseInstance`, иначе ref-count не уменьшится.
- Нужно не забывать **Build → New Build** контента перед билдом плеера, иначе старый каталог.
- Порог входа выше + накладные расходы на инфраструктуру для маленьких проектов.

## Ключевое для собеседования

- **Resources — legacy**, в новых проектах не используют (увеличивает размер билда и время запуска, неадресная выгрузка, строковые пути).
- **AssetBundles — low-level механизм**. Гибко, но весь учёт (зависимости, версии, дубли) ведёшь руками.
- **Addressables = AssetBundles + автоматизация** (адресация, ref-counting, анализ зависимостей, remote). **Дефолтный выбор** для загрузки контента.
- Главная мысль про Addressables: **отвязка ссылки от расположения** ассета и **управление памятью через подсчёт ссылок**.
- Главная ловушка: **leaks** — забытый `Release`.
