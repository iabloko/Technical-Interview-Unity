# Unity Garbage Collector

**Сборщик мусора (GC)** автоматически освобождает объекты в управляемой куче, на которые больше нет достижимых ссылок. Разработчику не нужно вызывать `delete` — но в Unity важно понимать, *как* GC работает, потому что его срабатывание вызывает **спайки кадра**.

## Какой GC использует Unity

Скриптовый рантайм Unity (и **Mono**, и **IL2CPP**) использует **Boehm–Demers–Weiser GC** — он заметно отличается от обычного .NET CLR GC:

| Свойство | Unity (Boehm) | .NET CLR GC |
|---|---|---|
| Тип | mark-and-sweep | mark-and-compact |
| Поколения (generations) | нет | да (gen 0/1/2) |
| Перемещение объектов | нет (non-compacting) | да (компактизация) |
| Сканирование | консервативное | точное |

- **Консервативный** — при обходе стека и регистров значения, *похожие* на указатели, считаются указателями. Поэтому GC не может безопасно перемещать объекты (вдруг это не указатель).
- **Non-compacting** — объекты не двигаются → куча **фрагментируется**.
- **Non-generational** — нет деления на поколения, поэтому каждый сбор обходит **всю** кучу: стоимость растёт с её размером.

## Как работает: Mark & Sweep

1. **Mark (пометка).** От «корней» (roots) — стек, регистры, статические поля — GC обходит граф объектов и помечает все **достижимые**.
2. **Sweep (очистка).** Всё непомеченное считается мусором, и эта память возвращается в список свободных блоков кучи (но не операционной системе).

```
[roots] → A → B      A, B, C достижимы → помечены (живые)
              ↘ C
          D            D недостижим → выметается (мусор)
```

## Когда запускается

- Когда очередной запрос на аллокацию **не помещается** в свободное место кучи. Тогда срабатывает GC; если места всё равно мало — куча **расширяется**.
- Вручную: `System.GC.Collect()` (обычно не рекомендуется в игровом цикле; иногда зовут на экране загрузки).

## Stop-the-world и спайки кадра

По умолчанию GC **синхронный**: он останавливает выполнение всего управляемого кода («stop the world») на время сборки. На большой/фрагментированной куче это даёт заметный **фриз кадра** — критично для 60 FPS и VR.

> Чем меньше и реже аллокации — тем реже и дешевле сборки. Это главная причина избегать `new` в `Update`.

## Incremental GC

Unity предлагает **инкрементальный сборщик** (Player Settings → *Use Incremental GC*). Он разбивает фазу **mark** на несколько кадров, используя *write barriers*, чтобы размазать паузу и убрать одиночный большой спайк.

Нюансы:
- общий объём работы GC может слегка вырасти;
- write barriers дают небольшой постоянный оверхед;
- если между «срезами» граф объектов сильно меняется, часть работы придётся переделать.

## Рост кучи

Куча Boehm в основном только **растёт** и почти не отдаёт память ОС. Один пиковый всплеск аллокаций надолго поднимает потребление памяти. Отсюда вывод: пиковые аллокации опаснее, чем кажется.

## Ручное управление

```csharp
// Принудительная сборка — уместна разве что на загрузочном экране
System.GC.Collect();

// Полное отключение GC на критичной секции (Unity 2019+), на свой риск:
GarbageCollector.GCMode = GarbageCollector.Mode.Disabled;
// ... горячая фаза без аллокаций ...
GarbageCollector.GCMode = GarbageCollector.Mode.Enabled;
```

> Отключать GC опасно: если в «отключённой» секции произойдут аллокации, куча будет только расти без сборки.

## Как снизить нагрузку на GC

- не создавать `new` и не боксить в `Update`/горячих путях;
- переиспользовать коллекции и буферы, применять **пулы объектов**;
- предварительно аллоцировать во время загрузки;
- избегать LINQ и замыканий в кадре;
- искать аллокации через **Profiler** (колонка *GC Alloc*);
- для тяжёлых вычислений — `NativeArray`/Job System/DOTS (нативная память **вне** GC);
- рассмотреть включение **Incremental GC** для более ровного кадрового времени.
