# ECS (Entity Component System)

ECS — архитектура DOTS, ориентированная на данные (data-oriented design, DOD). Противопоставляется классическому ООП-подходу Unity (`GameObject` + `MonoBehaviour`).

## Три понятия

| | Что это | Аналогия в GameObject-мире |
|---|---|---|
| **Entity** | лёгкий идентификатор (int + version), без данных и поведения | GameObject |
| **Component** | чистые данные (`struct : IComponentData`), без логики | поля компонента |
| **System** | логика: обрабатывает все entity с нужным набором компонентов | методы `Update` |

Ключевой принцип: **данные отделены от логики**. Компонент — только данные, система — только поведение.

## Зачем: data-oriented design и кеш

ООП хранит объекты вразброс по куче; обход дёргает память случайно → промахи кеша CPU. ECS хранит компоненты одного типа **плотно и непрерывно** в памяти (по архетипам), система проходит их линейно → кеш-дружественно. Плюс это раскладка, пригодная для [Job System + Burst](jobs-burst.md) и SIMD.

## Архетипы и чанки

Entity с одинаковым набором типов компонентов группируются в **архетип**; данные хранятся в **chunk'ах** (блоки фиксированного размера, ~16 КБ) колонками по компонентам. Добавление/удаление компонента переносит entity в другой архетип (structural change) — это не бесплатно, его батчат через `EntityCommandBuffer`.

## Запрос и система

```csharp
public partial struct MoveSystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;
        foreach (var (xform, vel) in
                 SystemAPI.Query<RefRW<LocalTransform>, RefRO<Velocity>>())
        {
            xform.ValueRW.Position += vel.ValueRO.Value * dt;
        }
    }
}
```

Система объявляет запрос (какие компоненты нужны) и обрабатывает все подходящие entity подряд.

## Когда оправдано (важно для собеседования)

ECS — не «всегда лучше». Выигрыш — на **большом числе однородных объектов** (тысячи юнитов, частиц, снарядов), где важна пропускная способность памяти и параллелизм.

Цена:
- Высокий порог входа, другой стиль мышления.
- Хуже для редких сложных уникальных объектов и UI.
- Совместимость со «старым» GameObject-кодом через baking/прослойки.
- Экосистема (ассеты, плагины) рассчитана на GameObject.

Часто применяют **гибрид**: критичный по нагрузке слой на ECS, остальное — на классике.

## Что спрашивают на собеседовании

- Что такое Entity/Component/System и почему данные отделены от логики.
- Зачем DOD: кеш-локальность, плотная раскладка vs разбросанные объекты в ООП.
- Что такое архетип и chunk, почему structural changes дороги.
- Когда ECS оправдан, а когда нет.
