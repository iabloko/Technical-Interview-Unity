# Графический конвейер (Graphics Pipeline)

**Графический конвейер** — последовательность этапов, через которые проходят данные сцены (вершины, текстуры, параметры), чтобы превратиться в финальное 2D-изображение на экране. Часть этапов выполняет **CPU**, основную работу — **GPU**. Понимание конвейера — база для разговора про производительность рендера, draw call'ы и шейдеры.

> Описание ниже соответствует конвейеру **растеризации** (Direct3D 11 / OpenGL / Vulkan, на которых работает Unity). Это не трассировка лучей — GPU не «пускает лучи», а проецирует треугольники на экран и закрашивает покрытые пиксели (про разницу см. [lighting.md](lighting.md)).

---

## Взгляд сверху: 4 концептуальных этапа

На верхнем уровне (модель из «Real-Time Rendering») построение кадра делится на 4 стадии:

```
1. Application (CPU)      → 2. Geometry (GPU)    → 3. Rasterization (GPU) → 4. Pixel (GPU)
   что рисовать,             вершины:                примитивы →             цвет каждого
   culling, draw calls       трансформации,          фрагменты (пиксели)     фрагмента,
                             проекция                                        тесты, запись
```

1. **Application (приложение, CPU).** Игровая логика, отсечение невидимого (culling), сбор геометрии, формирование и отправка **draw call'ов** драйверу. Здесь же — батчинг (в Unity: SRP Batcher, static/dynamic batching, см. [urp-render-pipeline.md](urp-render-pipeline.md)).
2. **Geometry processing (обработка геометрии, GPU).** Каждая вершина трансформируется из локального пространства модели в пространство экрана; считается проекция.
3. **Rasterization (растеризация, GPU).** Примитивы (треугольники) превращаются в **фрагменты** — кандидаты в пиксели.
4. **Pixel processing (обработка пикселей, GPU).** Для каждого фрагмента вычисляется цвет (текстуры, освещение), проходят тесты глубины/трафарета, результат пишется в кадровый буфер.

## Детально: этапы GPU-конвейера

Полная цепочка стадий GPU (по Direct3D 11). Часть стадий **программируемые** (вы пишете шейдер на HLSL), часть — **фиксированные** (конфигурируются, но не программируются):

| # | Стадия | Тип | Что делает |
|---|---|---|---|
| 1 | **Input Assembler (IA)** | фиксированная | Читает вершины и индексы из буферов, собирает из них примитивы (треугольники/линии/точки). |
| 2 | **Vertex Shader (VS)** | **программируемая** | Обрабатывает **каждую вершину**: трансформации (MVP), может считать свет per-vertex. Выполняется на каждую вершину. |
| 3 | **Hull → Tessellator → Domain** | прогр. + фикс. + прогр. | **Тесселяция** (опционально): дробит примитивы на более мелкие для детализации. |
| 4 | **Geometry Shader (GS)** | **программируемая** | Опционально: может **создавать/удалять** примитивы целиком (партиклы, билборды). |
| 5 | **Stream Output (SO)** | фиксированная | Опционально: запись обработанных вершин обратно в буфер (без отрисовки). |
| 6 | **Rasterizer (RS)** | фиксированная | Превращает примитивы в **фрагменты** (см. подробно ниже). |
| 7 | **Pixel Shader (PS)** | **программируемая** | Вычисляет **цвет каждого фрагмента**: сэмплит текстуры, считает освещение per-pixel. (= fragment shader в OpenGL.) |
| 8 | **Output Merger (OM)** | фиксированная | Тесты глубины/трафарета, смешивание (blending), запись в render target. |

> На собесе достаточно уверенно назвать костяк: **IA → Vertex Shader → Rasterizer → Pixel Shader → Output Merger**. Тесселяция, геометрический шейдер и stream output — опциональные стадии, их вставляют по необходимости.

## Geometry: трансформации координат (где «двигаются» вершины)

Vertex shader переводит вершину через цепочку систем координат. Это любимый вопрос на собесе:

```
Model space ──(Model matrix)──► World space ──(View matrix)──► View/Camera space
   │
   └──(Projection matrix)──► Clip space ──(перспективное деление /w)──► NDC ──(viewport transform)──► Screen space
```

- **Model (object) space** — координаты вершины относительно начала самой модели.
- **World space** — модель размещена в мире (позиция/поворот/масштаб объекта) → **Model matrix**.
- **View (camera) space** — мир пересчитан относительно камеры (камера в начале координат) → **View matrix**.
- **Clip space** — применена проекция (перспектива/орто), добавлена перспективная дисторсия → **Projection matrix**. Именно в clip space происходит **отсечение** (clipping).
- **NDC (Normalized Device Coordinates)** — после **перспективного деления** (x, y, z делятся на компоненту `w`). Куб `[-1..1]` (в D3D z: `0..1`).
- **Screen (window) space** — NDC растянут на размеры вьюпорта (пиксели экрана) → **viewport transform**.

> Три матрицы Model × View × Projection часто перемножают в одну **MVP-матрицу** и применяют к вершине за один умножение в вершинном шейдере.

## Rasterization: подробно (то, что чаще всего спрашивают)

Растеризатор — **фиксированная** стадия между геометрией и пиксельным шейдером. Берёт примитивы в clip space и выдаёт фрагменты. Внутри он делает несколько вещей подряд:

1. **Clipping (отсечение).** Отбрасывает примитивы (или их части) вне видимого объёма (view frustum), а также те, что за камерой (иначе деление на `w ≤ 0` сломает математику).
2. **Perspective divide (перспективное деление).** `x, y, z` делятся на `w` → переход из clip space в **NDC**. Это то, что даёт перспективу: дальние объекты «сжимаются».
3. **Viewport transform.** NDC `[-1..1]` масштабируется в пиксельные координаты экрана.
4. **Back-face culling (отсечение задних граней).** Треугольники, повёрнутые «спиной» к камере (по направлению обхода вершин — CW/CCW), отбрасываются: их всё равно не видно. Дешёвая, но важная оптимизация.
5. **Scan conversion (растеризация как таковая).** Определяется, какие **пиксели покрыты** треугольником → для каждого создаётся **фрагмент**.
6. **Attribute interpolation (интерполяция атрибутов).** Атрибуты вершин (нормали, UV, цвет) **интерполируются** по поверхности треугольника, чтобы у каждого фрагмента были свои значения (perspective-correct interpolation).

> **Фрагмент ≠ пиксель.** Фрагмент — «кандидат» в пиксель: на один пиксель экрана может прийтись несколько фрагментов (перекрывающиеся треугольники). Кто из них станет видимым пикселем — решает тест глубины в Output Merger.

## Pixel processing и Output Merger

- **Pixel (fragment) shader** — для каждого фрагмента вычисляет цвет: сэмплит текстуры, считает освещение per-pixel (`NdotL` и т.д., см. [lighting.md](lighting.md)). Самая нагруженная стадия на сценах с большим разрешением и **overdraw** (многократная перерисовка одного пикселя).
- **Output Merger** — фиксированная финальная стадия, комбинирует выход PS с буферами:
  - **Depth test (Z-test).** Сравнивает глубину фрагмента с Z-буфером; дальний за уже нарисованным — отбрасывается. Так решается видимость.
  - **Stencil test.** Маска по трафаретному буферу (порталы, контуры, эффекты).
  - **Blending (смешивание).** Для полупрозрачных — смешивание цвета фрагмента с уже записанным (alpha blending).
  - **Запись** результата в render target (кадровый буфер).

> **Early-Z (ранний тест глубины).** Логически depth test стоит в конце (Output Merger), но современные GPU выполняют его **до** пиксельного шейдера, если это возможно, — чтобы не считать дорогой шейдер для заведомо невидимых фрагментов. Поэтому порядок отрисовки (front-to-back для непрозрачных) влияет на производительность.

## Связь с Unity (для собеседования)

- **Draw call** = одна команда «нарисуй этот набор примитивов этим материалом». Много draw call'ов → нагрузка на CPU (Application stage). Снижают батчингом и [SRP Batcher](urp-render-pipeline.md).
- **Шейдеры в Unity** — vertex/fragment пишутся в HLSL или собираются в **Shader Graph**; это именно стадии VS и PS конвейера.
- **Overdraw** — проблема пиксельной стадии: прозрачные объекты и частицы рисуются поверх друг друга, пиксельный шейдер выполняется многократно на один пиксель. Частая причина просадок на мобилках/VR.
- **Forward vs Deferred** ([lighting.md](lighting.md)) — это про то, **на какой стадии и сколько раз** считается освещение пикселя, а не про сам костяк конвейера.

## Вопросы для самопроверки

1. **Назови основные стадии графического конвейера по порядку.** (IA → Vertex Shader → Rasterizer → Pixel Shader → Output Merger; между ними — опц. тесселяция/GS.)
2. **Какие стадии программируемые, какие фиксированные?** (Программируемые: VS, HS, DS, GS, PS. Фиксированные: IA, Tessellator, Rasterizer, Output Merger.)
3. **Через какие пространства координат проходит вершина?** (Model → World → View → Clip → NDC → Screen.)
4. **Что делает перспективное деление и где оно происходит?** (Деление на `w`, clip space → NDC, в растеризаторе; даёт перспективу.)
5. **Что конкретно делает растеризатор?** (Clipping, persp. divide, viewport transform, back-face culling, scan conversion, интерполяция атрибутов → фрагменты.)
6. **Чем фрагмент отличается от пикселя?** (Фрагмент — кандидат; на один пиксель может прийтись несколько фрагментов, видимый выбирает Z-тест.)
7. **Где и как решается, какой объект видим, если их несколько на одном пикселе?** (Depth test / Z-буфер в Output Merger.)
8. **Что такое Early-Z и зачем он?** (Тест глубины до пиксельного шейдера — не считать шейдер для невидимых фрагментов.)
9. **Что такое overdraw и на какой стадии он бьёт по производительности?** (Многократная закраска пикселя; пиксельная стадия — прозрачность/частицы.)
10. **Что такое draw call и почему их число важно?** (Команда отрисовки; много вызовов = нагрузка на CPU; снижают батчингом.)
