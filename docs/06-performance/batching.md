# Батчинг draw call'ов: Static/Dynamic Batching, SRP Batcher, GPU Instancing

## Проблема

Каждый **draw call** — это команда CPU → GPU отрисовать набор геометрии. Перед вызовом меняется состояние GPU (шейдер, текстуры, константы) — это **SetPass call**, самая дорогая часть. Много объектов → много вызовов → CPU становится узким местом (CPU-bound). Цель батчинга — сократить число SetPass/draw call'ов.

## Способы (в разных пайплайнах)

| Способ | Условие | Где |
|---|---|---|
| **Static Batching** | объекты помечены Static, не двигаются | Built-in + URP |
| **Dynamic Batching** | мелкие меши (≤ ~300 верт.), один материал | Built-in + URP (ограниченно) |
| **SRP Batcher** | один **шейдер** (варианты материала допустимы), совместимый шейдер | URP/HDRP |
| **GPU Instancing** | один меш + один материал, много экземпляров | оба |

## Static Batching

Статические меши с одним материалом объединяются в общие буферы вершин и индексов (при сборке сцены или через `StaticBatchingUtility.Combine`). Unity рисует их с меньшим числом изменений render state; число draw call'ов при этом не обязательно уменьшается. Цена — память: объединённая геометрия хранится отдельной копией. Только для неподвижных объектов.

## Dynamic Batching

Движок на CPU каждый кадр объединяет мелкие динамические меши с одним материалом в один буфер. Из-за CPU-затрат на трансформацию вершин выгоден только для очень простых мешей; иначе вредит. В современных пайплайнах роль невелика.

## SRP Batcher (URP/HDRP — главное)

Не объединяет меши в один draw call, а **ускоряет сами вызовы**: данные материалов хранятся в постоянных GPU-буферах и не загружаются заново на каждый объект. Батч прерывается при смене **шейдера** (variant), а не материала. Условие — шейдер должен быть SRP Batcher-совместимым (свойства в `CBUFFER` `UnityPerMaterial`).

Практический вывод: в URP для дешёвой отрисовки множества объектов держать **мало разных шейдеров**, а не мало материалов.

## GPU Instancing

Один вызов отрисовывает много экземпляров одного меша+материала, различающихся параметрами per-instance (матрица, цвет через `MaterialPropertyBlock`). Идеально для травы, толпы, пуль. Включается галочкой в материале (`Enable GPU Instancing`).

**SRP Batcher и instancing не складываются:** для обычных рендереров SRP Batcher имеет приоритет, поэтому instancing на материале сам по себе не сработает поверх него. Где instancing реально нужен — это процедурная отрисовка через `Graphics.DrawMeshInstanced` / `DrawMeshInstancedIndirect` (объекты без `GameObject`).

## Что ломает батчинг

- Разные материалы / разные текстуры (решение — атласы, texture arrays).
- Множественный лайтинг (доп. проходы), разные шейдер-варианты.
- `MaterialPropertyBlock` на рендерере делает его **несовместимым с SRP Batcher**; с GPU Instancing MPB совместим (per-instance свойства).
- `renderer.material` создаёт копию материала: static/dynamic batching и instancing она разрывает (разные материалы), SRP Batcher — нет (батч прерывается только сменой варианта шейдера), но копия занимает память и требует `Destroy`.

## Что спрашивают на собеседовании

- Что такое draw call и SetPass и почему их число важно.
- Чем SRP Batcher отличается от static/dynamic batching (ускоряет вызовы, прерывается по шейдеру, не объединяет меши).
- Когда применять GPU Instancing.
- Что ломает батчинг и как чинить (атласы, меньше вариантов шейдеров; `MaterialPropertyBlock` — для instancing, но он выводит объект из SRP Batcher).
